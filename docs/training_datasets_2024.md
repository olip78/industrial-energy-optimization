# Training datasets for 2024

The data pipeline materializes a shared canonical hourly table and three model-specific training datasets. All timestamps used internally are UTC; calendar features are derived in `Europe/Berlin`.

## Outputs

| Dataset | Target | Prediction setup |
|---|---|---|
| `canonical_hourly_2024.parquet` | none | joined hourly source layer with availability timestamps |
| `day_ahead_pv_2024.parquet` | `pv_power_mean_w` / `pv_energy_kwh` | one common D-1 decision time per delivery day, calendar and available ICON forecast |
| `oracle_pv_2024.parquet` | `pv_power_mean_w` / `pv_energy_kwh` | the same PV target rows with realised ERA5 weather |
| `day_ahead_price_2024.parquet` | `day_ahead_price_eur_per_mwh` | one common D-1 decision time, calendar, weather forecast and price lags |
| `mpc_pv_2024.parquet` | `pv_power_mean_w` / `pv_energy_kwh` | direct horizons from 1 through 10 hours |

This shared canonical build still does not place intraday prices in its manifest. Intraday price data is now handled by the separate audited MPC pipeline in `data/features/intraday_price/`: it uses Energy-Charts' hourly `Intraday Continuous Average Price (DE-LU)` as a realised settlement proxy and retains its own availability contract. See [`intraday_price_forecasting.md`](intraday_price_forecasting.md).

## PV development split

`day_ahead_pv_2024.parquet` includes a consecutive `week_index` only for model-development bookkeeping. It identifies a local calendar week and is not a predictive feature. The other datasets and the canonical table intentionally do not contain this column.

`SeasonalWeekSplitter` allocates whole weeks, rather than individual rows, to three partitions. Its default split is 70% train, 15% validation and 15% test. The allocation is random but deterministic for a given `random_state`, and occurs separately within winter, spring, summer and autumn. Therefore every partition contains observations from each season.

```python
import pandas as pd
from energy.data import SeasonalWeekSplitter

pv = pd.read_parquet("data/features/day_ahead_pv/day_ahead_pv_2024.parquet")
split = SeasonalWeekSplitter(random_state=42).split(pv)

train = split.train
validation = split.validation
test = split.test
```

Before fitting, exclude `week_index` from the feature list. For the final economic backtest, use a later chronological period rather than this season-balanced development split.

## Nested Oracle cross-fitting

`SeasonalWeekKFold` is the splitter used by the PV Oracle experiment. It places every whole week in one of five season-balanced test folds. The experiment uses this split twice:

1. For each outer test fold, the Oracle and forecast model are restricted to the remaining outer-training weeks.
2. Inside those outer-training weeks, an inner five-fold loop creates an out-of-fold Oracle proxy using forecast weather. This proxy is the feature supplied to the forecast model.
3. The final Oracle is fitted on all outer-training weeks, then produces the Oracle proxy for the outer test fold. The forecast model is evaluated on that test fold.

This nested design avoids the subtle leakage that occurs when an Oracle proxy for an outer-training row was generated by a model that had seen the target values in the outer test fold.

```bash
PYTHONPATH=src python scripts/run_pv_crossfit.py \
  --project-root . \
  --year 2024 \
  --outer-splits 5 \
  --inner-splits 5
```

The command writes row-level out-of-fold predictions, fold metrics and mean/pooled metrics under `artifacts/pv_crossfit/2024/`.
The metrics include three models: the actual-weather Oracle, the deployable forecast without an Oracle proxy (`baseline`), and the deployable forecast with the cross-fitted Oracle proxy (`forecast`).

## Leakage contract

Each sample contains `as_of_utc` and the availability timestamp of every time-dependent feature. Tests enforce that feature availability never exceeds `as_of_utc`. Each day-ahead target also has `target_available_at_utc`, which must be later than `as_of_utc`; this prevents an already-cleared auction price from entering a nominal forecast sample. Targets are present only for offline training and evaluation.

For day-ahead samples, `as_of_utc` is 11:00 Europe/Berlin on D-1 for all delivery periods of day D. This is a modelling choice that leaves one hour for submitting the position before a notional 12:00 gate closure. `horizon_hours` is the true elapsed time from that decision to the target period and therefore changes across the delivery day and at daylight-saving transitions.

## Known assumptions

- PV profile: MPVBench `1a`.
- PV source timezone: provisional `Europe/Berlin` conversion already documented in the project.
- PV values are aggregated from 15-minute mean power to hourly mean W and hourly kWh.
- The suspected common-source outages on 10 May and 7 July 2024 are excluded from PV training datasets.
- Day-ahead weather selects the freshest complete fixed-lead layer available at `as_of`: ICON `previous_day1` at 24 hours or `previous_day2` at 48 hours. These fields are point-in-time safe, but they still do not constitute one complete historical forecast run.
- Day-ahead price publication at 13:00 Europe/Berlin on D-1 is an explicit modelling assumption for availability checks.
- The archived weather fields begin during January 2024, so the first incomplete days are removed rather than imputed. MPC samples start after the 168-hour PV lag becomes available.

## Rebuild

After installing the package dependencies:

```bash
energy build-training-data \
  --project-root /path/to/energy \
  --year 2024
```

The repository script exposes the same command without installing the console entry point:

```bash
PYTHONPATH=src python scripts/build_training_datasets.py \
  --project-root . \
  --year 2024
```

The command also creates `data/curated/energy_training.duckdb`. It contains materialized copies of the canonical layer and all three training datasets, so the database remains usable if the project directory is moved.
